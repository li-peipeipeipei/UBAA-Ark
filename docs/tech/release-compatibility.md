# 版本兼容性：0.9.0 对 0.1.0 老版本的影响

> 结论先行：**已发布的 0.1.0 完全不受影响；`0.9.0` 覆盖升级也保留全部本地数据。
> 唯一的硬约束是签名必须与设备上已装版本一致，这一点在本地开发阶段需要留意。**

## 一、为什么「已发布的老版本」不会被影响

应用是**独立安装包**。用户手机上的 `0.1.0` 是一份已经编译好的二进制，
新代码不会回改它；学校后端也没有我们自建的服务端（客户端直连校内上游），
不存在「服务端升级导致老客户端不可用」的情况。

所以对**已经装了 0.1.0 的用户**：功能、登录态、行为都不变，直到他们主动升级。

## 二、覆盖升级（0.1.0 → 0.9.0）需要同时满足三条

| 项 | 要求 | 当前值 | 状态 |
|---|---|---|---|
| 包名 | 必须一致，否则是两个应用 | `com.ubaa.app` 未变 | ✅ |
| **签名** | 必须一致，否则系统拒绝覆盖 | 见下方「风险」 | ⚠️ |
| versionCode | 必须**严格大于**已装版本 | `1000000` → `1090000` | ✅ |

`versionCode` 只参与「能不能覆盖」的比较，与 `versionName` 没有算术关系。
历史取值：`0.1.0 = 1000000`、`0.9.0 = 1090000`。

## 三、⚠️ 唯一真实风险：签名不一致

当前 `build-profile.json5` 用的是 **DevEco 自动生成的调试证书**
（`keyAlias=debugKey`，存于 `~/.ohos/config/default_UBAA-HarmonyOS_*.p12`）。

这意味着：

- 设备上装的是**调试签名版** → 新包可直接覆盖安装，数据保留。
- 设备上装的是**上架用的 release 签名版** → 调试签名的包**装不上**
  （报签名校验失败），必须先卸载旧包再装 —— **卸载会清掉本地数据**
  （登录态、选过的学期/周次、课表缓存全部重来）。

上架同理：AGC 要求签名类型与申报一致，**调试签名的包会被拒收**。

**处理建议**：
1. 日常开发/自测：继续用调试签名，注意设备上装的也是调试版即可。
2. 要发给别人试用或提交 AGC 之前：在 DevEco 的 `Signing Configs` 里切回 release 证书
   （`keys/` 下有 `ubaa-release.p12`，但**口令只能从原签名配置取**，
   命令行 `hap-sign-tool` 复用不了 hvigor 的加密口令 —— 见
   `.backup/BUILD-PROFILE-RESTORE.md`）。

## 四、本地数据兼容性（升级不丢）

持久化全部集中在 `network/TokenStore.ets`，键名是稳定的字符串常量，
**0.9.0 一个都没改**：

| 键 | 用途 | 0.9.0 是否改动 |
|---|---|---|
| `access_token` / `refresh_token` / `*_expires_at` | 登录态 | 否 |
| `user_name` / `user_school_id` / `login_username` | 账户信息 | 否 |
| `selected_term_code` / `selected_term_name` | 选中学期 | 否 |
| `selected_week` | 选中周次 | 否 |
| `local_auth_session` / `local_connection_cookies` | 本地会话与 Cookie 罐 | 否 |
| `saved_credentials` | 记住的凭据 | 否 |
| `feature_usage` | 功能使用计数 | 否 |

课程/卡片缓存也是 Preferences 存 JSON，**key 与结构未变**。

> 注：`0.9.0` 修了 `AppStorage` 键名（`isDarkMode` → `isDark`），但那是**运行期内存键**，
> 不落盘，与升级无关 —— 只影响本次运行的主题判断。

## 五、行为层面的变化（升级后用户能感知的）

| 变化 | 影响 |
|---|---|
| 评教能正常进列表 | 修复，原先一直报会话失效 |
| 首页点课程弹出完整详情（9 行） | 修复，原先是 2 行 |
| 深色模式状态栏/渐隐条颜色正确 | 修复 |
| 顶层多出「财务收入」「网费流量」两个入口 | 新增，不影响既有入口 |
| 首页会按**当前学期**取数 | 修复：原先可能停在过期学期（考试倒计时也会随之变正确） |

## 六、`minAPIVersion` 未变

`minAPIVersion: 23`、`compatibleSdkVersion: 6.1.0(23)`、`targetAPIVersion: 23`。
**没有提高最低系统版本**，所以原先能装 0.1.0 的设备，0.9.0 一样能装。
