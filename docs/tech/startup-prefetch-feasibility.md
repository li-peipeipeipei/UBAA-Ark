# 启动预加载可行性研究（使用频率前五功能）

> 结论先行：**不做「五个功能一起预取」**。按「参数确定性 + 数据复用度 + 首帧影响」筛选后，
> 只预取 3 份数据 + 1 次会话唤醒，并全部放在**首帧之后**、只写内存缓存不碰界面。
> 已按此方案落地（`common/StartupPrefetch.ets` + `common/MemoCache.ets`）。

## 一、判据：什么才算「可预取」

预取的成本不只是流量，还包括：首帧被拖慢、Cookie 罐并发写、启动阶段耗电。
所以先定三条硬门槛，缺一不预取：

1. **参数确定**：不依赖用户在页面上做选择。需要选校区/日期/筛选条件的功能，预取只能猜参数，
   猜错就是白跑一次请求（还占着 Cookie 罐）。
2. **可复用**：同一份数据至少被两个入口读取，或者能被「下一次打开」直接命中。
3. **不写界面**：预取结果只进缓存，绝不驱动首帧。凡是「预取回来直接 setState」的做法，
   会让启动动画末尾多一次重排（详见第四节）。

## 二、前五功能逐项评估

「使用频率前五」按 `components/FeatureRegistry.ets` 里已声明的顺序（该顺序就是按一学期
使用频次排的）取前五：考试 / 成绩 / 空闲教室 / 阳光打卡 / 博雅课程，再加上两个**常驻面**
（首页、课表页）。

| 功能 | 首屏请求 | 参数确定性 | 复用度 | 结论 |
|---|---|---|---|---|
| 课表（含首页课程详情） | `terms` → `weeks` → `weekly(term,week)` | ✅ 全部可由「当前学期 + 当前周」推出 | ✅ 首页、课表页、课程详情弹窗**三处共用** | **预取** |
| 考试安排 | `exams(term)` | ✅ 只需学期 | ✅ 首页倒计时 + 考试页 | **预取** |
| 成绩查询 | `grades(term)` | ✅ 只需学期 | ⚠️ 仅成绩页，但可消除一次额外 CAS 换取 | **预取（最后一步）** |
| 空闲教室 | `classroom(campus,building,date,section)` | ❌ 依赖用户选校区/教学楼/日期 | ❌ 首页不复用 | **不预取**（猜参数只会白跑） |
| 阳光打卡 | oauth 链 → 概览 + 记录 | ⚠️ 参数确定但**要额外走一条 ≤10 跳的 oauth 链** | ❌ 仅本页 | **不预取**（冷门且链最长） |
| 博雅课程 | `bykc(cas)` → 列表（带筛选） | ❌ 依赖筛选条件 | ❌ | **不预取** |
| 首页今日课程 | `today(rq=今天)` | ✅ | 仅首页 | 页面自己首屏就拉，**缓存共享即可** |

> 「阳光打卡/博雅不预取」不是偷懒：它们的首次打开成本主要在**认证跳转链**而非数据量。
> 为一次可能用不到的跳转付 10 跳握手，收益是负的。真要优化，正确做法是在用户**进入该页签**
> 时预热（已由页面自身的 `ensureLogin` 单飞完成）。

## 三、方案对比

| 方案 | 首帧影响 | 实现成本 | 失败隔离 | 结论 |
|---|---|---|---|---|
| **A. AppStartup 启动框架 + taskPool** | 可配置 `waitOnMainThread:false`，不阻塞首帧 | 中（`startup_config.json` + `@Sendable` 任务类 + `module.json5` 注册） | 好 | **不采用**（见下） |
| **B. `onCreate` / `onWindowStageCreate` 里直接预取** | ❌ 直接拉长首帧，官方明确反对 | 低 | 差 | 不采用 |
| **C. 首帧后应用内调度（本次采用）** | ✅ 首帧后才开始 | 低 | 好（每步独立 try/catch） | **采用** |
| **D. 组件预创建（`NodeController` / `builderNode` 预渲染）** | ⚠️ 预建节点会占内存与首帧 CPU | 高 | 中 | 不采用（收益不明确，且与快照一致性冲突） |
| **E. 读穿缓存（服务层 TTL + 单飞）** | ✅ 零影响 | 低 | 好 | **采用（作为 C 的底座）** |

### 为什么不用 AppStartup

官方文档（`harmonyos-guides/app-startup`）给的能力完全够用：`schedulerPhase: preAbilityStageLoad`
可让任务与 AbilityStage 加载并发，`runOnThread: taskPool` + `waitOnMainThread: false` 不阻塞首帧。
但对**这个应用**不划算：

1. **首帧依赖这些值**。首帧要用到 `isDark`、断点、登录态、`TokenStore` 的 clientId —— 这些
   必须在 `onCreate` 同步就绪，搬进 taskPool 反而要加一层等待。
2. **网络请求不适合 taskPool**。RCP/HTTP 本身是异步的，放进 taskPool 只是把「发起」挪走，
   IO 并未并行化；而结果回主线程还要跨线程传递（`@Sendable` 约束）。
3. **收益只有「本地 Prefs 预热」**，而 EntryAbility 里那几项已经是最小集（各一次 `getSync`）。
4. **风险与验证成本不匹配**：`appStartup` 配置写错会导致启动即失败，本轮**没有真机**可验证。

留作演进：若以后引入 HSP/HAR 拆分或 Native so，再按官方示例接入（配置形态已在文档里确认）。

## 四、与「打开动画中的快照」的关系（本次处理的重点）

系统在启动/切回前台时会用 **startWindow（图标 + 背景色）** 或**上一帧快照**参与动画。
预取若处理不当，会在这两个环节露出破绽：

| 风险 | 表现 | 本次做法 |
|---|---|---|
| 首帧前发请求 | 启动动画变长，动画结束还在转圈 | 预取延迟到 **首帧后 900ms** 才开始 |
| 预取直接驱动 UI | 动画结束瞬间「空 → 满」跳一下，甚至闪两下 | 预取**只写内存缓存**，不碰任何 `@State` / `AppStorage` |
| 首帧后新增 AppStorage 键 | 订阅组件在动画末尾重建 | 不新增键（首帧用的键全部在 `onCreate` 建好） |
| 启动窗口底色 ≠ 首帧底色 | 动画最后一帧颜色突变（白 → 浅灰） | `start_window_background` 由 `#FFFFFF` 改为 **`#F1F3F5`**，与 `page_background` 完全一致（深色本来就是 `#000000`，无需改） |
| 转屏/折叠触发全量推卡 | 转场动画期间做同步 IO | 上一轮已修：`onConfigurationUpdate` 只在深浅色真变时 `pushAll` |

**一句话原则**：预取只负责「数据先到」，不负责「界面先变」。界面变化仍由各页面自己的
加载状态机驱动 —— 与没有预取时走同一条路径，只是 `await` 更快返回。

## 五、实施内容

### 1. `common/MemoCache.ets`（新增）

- **TTL**：页面的数据新鲜度需求不同，统一按秒级给；只承担「同一次启动内去重」，
  不承担离线可用（离线看课表由 `ScheduleCache` 磁盘缓存负责）。
- **单飞（single-flight）**：同一 key 的并发请求合并成一次。这一条的作用不只是省流量 ——
  首页与课表页同时启动时，两个请求会各自「整罐读 → 改 → 整罐写」Cookie，后写的会覆盖前者。
- **`force` 逃逸口**：用户显式刷新必须绕开缓存。

### 2. `network/LocalAcademicService.ets`（改造）

`fetchTerms` / `fetchWeeks` / `fetchWeeklySchedule` / `fetchTodayClasses` / `fetchExams` /
`fetchGrades` 全部改为「缓存包装 + `doFetchXxx` 真实实现」，并新增可选 `force` 参数。

TTL：学期 60s / 周次 120s / 周课表 30s / 今日课程 20s（key 含日期）/ 考试 60s / 成绩 60s。

`reset()` 里追加 `MemoCache.clear()` —— **换账号或切连接模式必须清**
（两种模式的 Cookie 完全不同，缓存里是另一个会话的数据）。

### 3. 刷新路径传 `force = true`（必须，否则「下拉了没变化」）

| 位置 | 原因 |
|---|---|
| `SchedulePage` 逐周与上游比对（2 处） | 不绕缓存就是拿自己刚缓存的那份去比，永远比不出差异 |
| `SchedulePage.reloadWeek`（下拉刷新/切周） | 用户显式刷新 |
| `HomePage.loadHome(!showLoading)` | 下拉刷新时绕开，首次加载允许命中 |

### 4. `common/StartupPrefetch.ets`（新增）

- 首帧后 **900ms** 启动，总预算 **9s**，**串行**执行（同一个 Cookie 罐不适合并发）；
- 顺序：`terms`（顺带打通教务会话）→ `weeks` → 当前周 `weekly` → `exams` → `grades`（最重，最后）；
- 每步独立 try/catch；超预算 / 切后台 / 已登出 → 立即停手（`EntryAbility.onBackground` 调 `cancel()`）；
- 全程只写 `MemoCache`，日志带每步耗时（`hilog` 关键字「启动预取」），便于真机核对收益。

### 5. 直接收益（无需改页面代码）

页面仍在 `aboutToAppear` 里照常 `await ApiService.xxx()`，但此时缓存已热：
`await` 在微任务内返回，**LOADING 态几乎不落帧**，二级页表现为「点开即有内容」。

## 六、验证方法（真机）

1. `hilog | grep 启动预取` —— 看每步耗时与是否在 9s 内完成。
2. 冷启动 → 停在首页 2s → 切课表页：应**不再出现**「第 N 周加载中…」。
3. 首次进成绩页：应从「加载中」直接出内容（若第一步预取被切后台取消，则会正常加载）。
4. 下拉刷新课表：必须真的重新请求（抓 `hilog` 的 `周课表 ... 门课` 条数应增加一次）。
5. 登出再登录：预取应重新跑一次（`StartupPrefetch.reset()`）。

## 七、风险与回滚

| 风险 | 影响 | 回滚方式 |
|---|---|---|
| 缓存给了过期数据 | 最多 30~120s 的旧值；显式刷新已 `force` | 调小 TTL 或删除 `MemoCache.through` 调用 |
| 预取拖慢首屏 | 已延迟到首帧后且异步；失败静默 | 注释 `MainPage.aboutToAppear` 里的 `StartupPrefetch.start()` |
| 登出后残留上一账号数据 | 已在 `LocalAcademicService.reset()` 清缓存 | —— |
| 内存占用 | 6 类数据，均 KB 级 | —— |

## 八、未做（明确取舍）

- **空闲教室 / 博雅 / 阳光打卡**：参数不确定或认证链过长，预取收益为负（见第二节）。
- **AppStartup 启动框架**：见第三节的四条理由；留作 HSP/HAR 拆分后的演进项。
- **组件预创建**：与「首帧稳定」目标冲突，且无设备无法验证内存与首帧影响。
